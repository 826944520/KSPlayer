1. 强制“日志驱动”的修复闭环（信息透明化）
编译报错有明确的行号和原因，但运行时错误往往只有模糊的堆栈。必须强制AI遵循“先加日志，再复现，最后修改”的铁律。

实施方法：在提示词中规定，对于无法通过编译阶段验证的逻辑，AI必须先注入结构化日志（关键变量值、分支命中情况、耗时），然后全量运行一次测试。

防循环机制：将运行日志作为“唯一事实来源”。如果AI修改代码后，重新运行产生的新日志与旧日志在出错前的关键变量完全一致，说明修改无效，此时直接触发熔断，不再允许AI继续尝试。

2. 构建“测试用例契约”（结果判定标准化）
实测最大的问题是“结果怎么算对”。不能让AI凭感觉看输出，必须将判定标准固化为自动化断言（Assertions）。

分级验证：

冒烟测试（必须100%通过）：进程不崩溃、无内存泄漏、主流程不抛异常。

核心业务测试（设定容错率）：如果涉及数值计算或AI模型输出，允许一定误差（如±5%），但必须由脚本自动计算误差，而非AI肉眼判断。

防循环策略：引入“回归测试集”。要求AI修复新Bug时，必须额外运行一个包含历史典型场景的测试集。如果新代码导致旧的Pass用例失败（即引入新Bug），则强制回退代码并增加一次“回归修复”计数，计数达到2次即停止并呼叫人工。

3. 环境隔离与“快照回放”（消除不确定干扰）
实测失败的很大原因是环境“脏”了（如数据库残留、网络抖动、缓存影响）。AI如果针对脏数据改代码，必然陷入死循环。

环境快照：每次实测前，从基线（Docker镜像或数据库DUMP）完全重建测试环境。确保每次实测的起点100%一致。

流量回放：如果涉及网络请求，使用录制的请求包（如.har文件或gRPC的dump）进行回放，而非实时请求外部服务。这样能确保AI每次面对的输入是确定的，它只需专注修复逻辑，而不用纠结“为什么这次请求返回了503”。

4. 引入“渐进式暴露”与“黄金指标”（运行时观察）
有些问题（如死锁、高并发下的竞态条件）单次运行看不出来，需要在特定压力下才暴露。

渐进式策略：让AI先通过单线程单元测试，再通过低并发（2-5路）集成测试，最后才是高并发稳定性测试。

熔断依据：不要让AI去分析复杂的火焰图，而是给它设定几个“黄金指标”（如：P99延迟增加超过10%、CPU毛刺超过阈值）。如果AI修改代码后，黄金指标恶化，直接判定为“负优化”，舍弃本次修改，并明确告知AI“本次改动降低了性能，请尝试保持性能不变的方案”，以此限制AI的搜索空间，避免它在性能陷阱里打转。

💡 终极兜底：引入“人类思维模拟”机制
当以上流程都走完，AI依然改不好时，强制AI切换思维模式：

第一次失败：AI被要求输出“故障树分析（FTA）”，列出所有可能导致此运行时错误的假设。

第二次失败：AI被要求“最小化复现路径”——即删减无关代码，只保留能触发Bug的最小片段。如果抽离后Bug消失，说明是环境耦合问题，AI必须放弃修改主代码，转而编写适配层（Wrapper）或重试退避策略。

第三次失败：自动生成一份包含所有尝试、日志和假设的调试报告，推送给开发者。程序自动终止，绝不尝试第四次。
